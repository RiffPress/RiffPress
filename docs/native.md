# What WordPress has, and what Riff adds

The Media Library is where Riff's music lives. Riff uses what WordPress already has, and adds something only where WordPress has no equivalent. Each addition below says why it exists, and links the core ticket when there is one. An addition that lands in core is deprecated in Riff and then removed, following the stability rule in the plugin readme.

When you add storage, a field, a relation or a query to Riff, add a row here in the same pull request.

## Used as WordPress has it

| What | Where it lives in WordPress |
| --- | --- |
| A track | An audio attachment. |
| Title, artist, album, year, genre, track number, length | Read from the file's tags by getID3 on upload (`wp_read_audio_metadata()`), kept in `_wp_attachment_metadata`. |
| Bit rate, sample rate, bit depth, codec, lossless | The same upload metadata. |
| Lyrics | The file's lyrics tag (ID3 USLT), which WordPress reads on upload into the same metadata as `unsynchronised_lyric`, and the media REST route returns in `media_details`. Riff Lyrics shows it, and its Media Library field edits that same key. |
| Artwork | The attachment's featured image. WordPress saves artwork embedded in the file as an image and sets it on upload; Riff's Artwork field in the Media Library sets the same featured image. |
| A cover's alt text | The image's own alt text, `_wp_attachment_image_alt`, as the Image block reads it; a cover Riff draws names the album and artist it draws. |
| A video's captions | The video block's text tracks, read from the block; the Media Library field above for a video with no block. |
| Where a track appears | The audio, video and playlist blocks in posts. |
| A track's details in a Heading, Paragraph or Image | Block Bindings: Riff registers the `riff/track` source, and core fills the block from it on the front end. Core decides which attributes a source can fill (a paragraph's, heading's and list item's content, an image's url, alt, title, id and caption, a button's text and link, and a few more); in the editor the block shows that it is bound, since Riff registers no editor-side source. |
| A shared playlist | A post with the Playlist block (WordPress 7.1). |
| A listener's own playlist | A private post of Riff's `riff_playlist` type, written by the listener, holding one Playlist block (WordPress 7.1) whose playlist-track blocks are its tracks in order. |
| Who can play what | The status and visibility of the post a track appears in. |
| People and app sign-in | WordPress users and application passwords. Riff Sign In signs listeners in with the same cookie, `wp_set_auth_cookie()`, and makes new accounts only when "Anyone can register" is on. With Riff Sign In's Listeners setting on Settings › General, people who cannot write posts are kept to their profile in wp-admin, by their own capabilities rather than a role of Riff's. |
| AI tools and other plugins reading the library or keeping likes and playlists | The Abilities API: Riff registers one ability per `riff/v1` route it answers for, each run as that route's REST request, except the player's own `riff/v1/together`. |
| A track's artist, album, video version, captions and protection in the Media Library's views and forms | The Entity Fields API (WordPress 7.2; on 7.1 the same fields are on the attachment's edit screen): Riff registers each as a field of the attachment entity, reading and writing a REST field of the same name on `wp/v2/media`, so DataViews shows and edits them beside core's own without a screen of Riff's. |
| Per-site upload limits on a network | Multisite's `blog_upload_space`. |

## Added by Riff, and why

| Gap | What Riff adds | Why | Upstream | Status |
| --- | --- | --- | --- | --- |
| No link between a song and its video | `_riff_video` post meta on the audio attachment, set from the Media Library's Video version field | Core has no relation between two attachments. | None filed | In Riff |
| No captions for a video outside a post | `_riff_captions` post meta on a video attachment, pointing at a WebVTT file in the Media Library, set from the Media Library's Captions field | The video block keeps its text tracks on the block, so a video version chosen in the Media Library, which no block holds, has nowhere to name one. A video block's own tracks are read as they are. | None filed | In Riff |
| The file's language tag is read and dropped | `language` in `_wp_attachment_metadata`, kept from getID3's tags on upload through the `wp_read_audio_metadata` filter | A title in another script needs a `lang` attribute for a screen reader to pronounce it, and the file's tag says what it is. `wp_add_id3_tag_data()` keeps an MP3's TLAN as written, a three-letter code such as `fra` where `lang` wants `fr`, and reads only ID3, so a FLAC, Ogg or M4A file's tags, the language among them, are not kept at all. | Not yet | In Riff |
| A FLAC, Ogg or M4A file's tags are read and dropped | `Media::tags()` on the `wp_read_audio_metadata` filter keeps them in `_wp_attachment_metadata` under the names ID3 gives the same tags (`albumartist` as `band`, `date` as `year`, `tracknumber` as `track_number`), leaving any WordPress kept | `wp_add_id3_tag_data()` reads only ID3, so these files keep no title, artist or album, and the catalog has nothing to file them by. | [Core #66417](https://core.trac.wordpress.org/ticket/66417) | In Riff |
| No waveform for an upload | Levels from the demo seed only; uploads have none yet | Drawing a waveform otherwise means fetching the whole file in the browser, as the Playlist block does. | [Gutenberg #84712](https://github.com/WordPress/gutenberg/issues/84712): measure peaks once at upload | Proposed upstream |
| Albums and artists can't be browsed or queried; they sit in serialized `_wp_attachment_metadata` | `riff_album` and `riff_artist` taxonomies on attachments, filed from the file's album, artist and band tags whenever its metadata is saved; an album's artist is `riff_album_artist` term meta; `_riff_catalog` marks a file filed, and a background job files a library from before, walking it by ID from where its last batch stopped, which `riff_catalog_backfill_from` keeps (`wp riff catalog` does it at once) | Taxonomies on attachments are native: the Media Library shows them as columns and filters, and REST and `WP_Query` can query them. A track's edit screen has no box for either: core's tag box splits names on commas, which artist and album names are full of, so the core Metadata box's Artist and Album are where a track is filed. Search and browsing need something queryable ([#343](https://github.com/RiffPress/RiffPress/issues/343), [#366](https://github.com/RiffPress/RiffPress/issues/366)). | Not yet | In Riff |
| No place for an image a plugin generates | A drawn cover, once drawn, is kept as an SVG file in `uploads/riff-art/{version}/`, and pages link to the file; `riff_art_stamp` names the drawing, and moves when a post, a track's tags or levels, or an album changes. The folder before stays for a page cached a moment ago; a post that stops being public takes every folder. | Drawn at `?riff-art`, every cover started WordPress for each request, and a signed-in listener passes every page cache, so one Home view queued about twenty requests on the host's few PHP workers. Core keeps an attachment's image sizes as files beside it for the same reason, but a drawn cover is no attachment. | Not yet | In Riff |
| No colour for an image | `_riff_tint` attachment meta on a cover image: its most colourful shade, read from the thumbnail's pixels the first time an album page shows it ([#396](https://github.com/RiffPress/RiffPress/issues/396)) | Standalone mode tints an album's header from its cover, as the streaming apps do. Reading the pixels on every page view would be slow, and the colour belongs to the image. | Not yet | In Riff |
| No artwork for an album | Planned: term meta on `riff_album` pointing to an image attachment | The cover stays an image in the Media Library. | Not yet | Planned |
| No picture for an artist | `riff_artist_image` term meta on a `riff_artist` term, pointing at an image in the Media Library, set from an Image field on the artist's edit screen ([#397](https://github.com/RiffPress/RiffPress/issues/397)) | The artist page leads with a picture, as the apps' do. The picture stays an image in the Media Library; without one, the artist's newest album cover is used. | Not yet | In Riff |
| Playlists that belong to a listener, not to the site | The `riff_playlist` post type: private, out of archives, feeds and search, listed under Media in the admin, opening in the block editor, with its tracks in core's Playlist block; made and changed through `riff/v1/users/me/playlists` ([#401](https://github.com/RiffPress/RiffPress/issues/401)) | A playlist is a post holding a Playlist block, so it needs no table, keeps its order and duplicates as the block does, and edits in the editor. Its own type keeps listeners' private lists out of the blog and its Posts grid, and lets a listener own one without the right to publish posts. | Not yet | In Riff |
| No likes or listening history for a user | The `riff_likes` and `riff_history` user options (user meta under the site's table prefix, so each site on a network keeps its own), read and written through `riff/v1/users/me/likes` and `riff/v1/users/me/history`; a visitor's stay in their browser as `riff-likes` and `riff-history`, and join their account when they sign in ([#400](https://github.com/RiffPress/RiffPress/issues/400)) | Likes belong to a user and are a short list of IDs, which user meta holds without a table of its own. Visitors have no user, so their browser keeps theirs until they have one. | Not yet | In Riff |
| No way to install a site's player as an app | A web app manifest at a Listen page's `app/` address, and that address rendering the player outside the theme ([#379](https://github.com/RiffPress/RiffPress/issues/379)) | Browsers install a page that names a manifest; WordPress has no manifest of its own. The desktop app loads the same address. | Not yet | In Riff |
| Every upload is a public file, whatever post it belongs to | An opt-in **Protected** box that moves an audio or video file into a folder the web server refuses, and serves it at `?riff-file=ID` to whoever may play it, with byte ranges; `_riff_protected` attachment meta keeps the file's original place, and `riff_protected_dir` names the folder ([#406](https://github.com/RiffPress/RiffPress/issues/406)) | Hiding a private post's tracks means little while the file plays for anyone with its address. Core serves uploads straight from disk and has no permission check on a file. | [Core #17255](https://core.trac.wordpress.org/ticket/17255): statuses for media, which restricted access was closed as a duplicate of | In Riff |
| No passkeys, and no sign-in without a password | Riff Sign In, a plugin beside Riff: `riff_passkeys` user meta holding each passkey's public key, `riff_passkey_id` for the lookup and `riff_passkey_handle` for the authenticator's handle; a code sent to an email as a transient for ten minutes ([#431](https://github.com/RiffPress/RiffPress/issues/431)) | Core signs in with passwords, and application passwords are for apps. Listeners of a music site should not need a password to keep their likes. | [Core #55950](https://core.trac.wordpress.org/ticket/55950): passwordless sign-in with passkeys | In Riff Sign In |
| No way to see who else on the site is listening, or to listen along | With the [Presence API](https://github.com/WordPress/presence-api) feature plugin active, a row for each signed-in listener who is playing, `riff-{user ID}`, in its `riff/listening` room: their queue as track IDs, where they are in it, whether it plays, and the server's time then. Read and written through `riff/v1/together`, which turns the IDs back into the tracks each reader may see ([#687](https://github.com/RiffPress/RiffPress/issues/687)) | Presence is written every few seconds and gone in minutes. In options or user meta that would invalidate caches site-wide, which is why the Presence API keeps it in a table of its own with an expiry. Its own REST routes need `edit_posts`, so a listener can't call them, and Riff calls its PHP API behind a route of its own. | The Presence API, proposed for core | In Riff, with the Presence API |
| No bulk import from a folder | `wp riff import`, a thin layer over `media_handle_sideload()` ([#367](https://github.com/RiffPress/RiffPress/issues/367)) | Every file goes through core's own upload path, so its tags and artwork are read the way an upload's are. | Not yet | In Riff |
| No way to tell a file was already uploaded | `_riff_import_hash` attachment meta (the file's SHA-1), and `_riff_import_folder` post meta on an album post | Running an import again must not duplicate the library, and new tracks must join their album. Core has no content hash on attachments. | Not yet | In Riff |
| A real AAC `.m4a` is refused: core lists `m4a` as `audio/mpeg`, then the file's sniffed type, `audio/mp4`, doesn't match; `.opus` isn't listed at all | During `wp riff import` only, `m4a` is allowed as `audio/mp4` and `opus` as `audio/ogg` | Both are common in music libraries, and the person running the command chose the folder. Uploads through the Media Library are unchanged. | Not yet | In Riff |

## Private core APIs Riff still uses

Core can change these without notice. Each has no public equivalent yet; the API coverage report (`npm run api-coverage`) lists them under "Private APIs in use".

| What | Where | Why | Upstream |
| --- | --- | --- | --- |
| `_wp_render_title_tag`, `_block_template_render_title_tag` and `_block_template_viewport_meta_tag`, unhooked from `wp_head` | `Standalone::template()` | Standalone mode's document prints its own title and viewport, and a second viewport later in the head would drop `viewport-fit=cover`. Core has no public way to stop printing either tag; its filters change the title's text, not whether the tag is printed. | [Core #59510](https://core.trac.wordpress.org/ticket/59510) proposes a filter for the viewport tag; [#61900](https://core.trac.wordpress.org/ticket/61900) asked for the title and was pointed at `pre_get_document_title` |
| `__experimentalBorder`, `__experimentalSkipSerialization`, `__experimentalFontFamily`, `__experimentalLetterSpacing` and `__experimentalDefaultControls` in the Listen block's `block.json` | `features/listen/block/block.json` | The block's border and font controls, and its colours and font family applied to the views inside it rather than to the wrapper. WordPress 7.1 has no stable key for any of them; switch when it does. | [Core #61728](https://core.trac.wordpress.org/ticket/61728), closed after Gutenberg reverted the stable keys; [Gutenberg #63001](https://github.com/WordPress/gutenberg/issues/63001) and [#64312](https://github.com/WordPress/gutenberg/issues/64312) are open |
